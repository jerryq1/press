# 微调整体流程

大语言模型监督微调（Supervised Fine-Tuning, SFT）的整体流程可归纳为四个核心环节：**模型选择 → 数据准备 → 微调训练 → 模型验证**。各环节环环相扣，且在实践中并非一次性线性执行，而是贯穿整个项目的**迭代优化过程**——验证结果将反馈至数据准备和训练环节，驱动持续改进，直至达到预期的任务效果。


## 1. 模型选择

模型选择是微调的首要决策，核心回答两个问题：选什么类型？选多大参数量？

### 1.1 类型选择：Base Model vs Instruct Model

实践中，模型类型选择遵循一条核心原则：

> **绝大多数场景应优先选择 Instruct Model，仅当任务高度定制化或需从零开始深度适配时，才考虑 Base Model。**

两类模型的对比如下：

| 对比维度 | Instruct Model | Base Model |
|---------|---------------|------------|
| 是否具备指令理解能力 | ✅ 已具备 | ❌ 需从头学习 |
| 是否经过偏好对齐 | ✅ 是 | ❌ 否 |
| 数据准备难度 | 低 | 高 |
| 训练难度 | 低 | 高 |
| 典型适用场景 | 客服问答、内容生成、结构化输出、多轮对话 | 任务形式非常特殊、拥有海量高质量领域数据 |

**领域适配的补充考虑**：对于医疗、法律、金融等专业领域，选型时还需额外关注：
- 该领域是否有专用的领域模型（如医学领域的 PMC-LLaMA、法律领域的 LawBERT 等），领域模型通常已在相关语料上进行了增量预训练或专项微调，效果起点更高；
- 通用模型在该领域公开基准（如医学问答基准、法律判决预测基准）上的评测表现，可作为选型参考依据；
- 领域数据的量和质量是否足以支撑较大模型的微调——数据量不足时，大模型反而更容易过拟合。

### 1.2 规模选择：参数量级权衡

模型规模选择的核心原则是：

> **参数量越大能力越强，但显存、训练和推理成本同步攀升，应根据任务复杂度与资源条件综合决策，并非越大越好。**

常见任务选型参考如下：

| 任务类型 | 推荐参数量级 |
|---------|------------|
| 意图识别、文本分类 | 1B–7B |
| 智能客服FAQ、工单辅助 | 7B–14B |
| 企业知识库问答、RAG | 7B–14B（起步），复杂场景14B–32B |
| NL2SQL（简单场景） | 7B–14B |
| NL2SQL（复杂场景） | 14B–32B |
| 本地轻量部署、边缘设备 | 0.5B–4B |

### 1.3 实践策略

建议采用**渐进式验证策略**：

1. **基线实验**：从 7B/8B 或 14B 级别的 Instruct Model 起步；
2. **任务评测**：在目标任务上验证效果；
3. **按需升级**：若复杂推理、长上下文理解或结构化输出稳定性不足，再考虑升级至 32B 或更大模型。

> ⚠️ 上述参考仅作为初始选型依据，最终应以实际任务评测结果为准。


## 2. 数据准备

数据准备是决定模型能力上限的基础环节——**高质量数据是高质量微调的前提**。

### 2.1 数据来源

| 类型 | 具体来源 |
|------|---------|
| 公共数据源 | HuggingFace、ModelScope 等开源社区与平台 |
| 私有数据源 | 企业内部文档、客户反馈记录、业务数据库等 |

### 2.2 数据处理流水线

原始数据通常无法直接用于训练，必须经过以下标准化处理流程：

| 步骤 | 说明 |
|------|------|
| **筛选** | 剔除无关、低质量或重复数据 |
| **清洗** | 去除噪声、统一格式、处理缺失值 |
| **结构化** | 按任务要求组织数据格式 |
| **答案构造（目标输出生成）** | 为每个输入构造高质量的期望输出，这是 SFT 数据准备中最关键的环节——直接决定了模型学习的目标方向 |
| **格式转换** | 转换为模型训练所需的输入输出格式（如对话模板、指令-回答对等） |

> **注意**：在 SFT 场景中，“答案构造”与传统机器学习中的“数据标注”有本质区别——不是给样本贴类别标签，而是为每条指令精心撰写一个完整、准确、风格一致的期望回答。回答质量直接决定了微调效果的上限。


## 3. 微调训练

训练阶段是模型真正进行参数调整、适配目标任务的核心执行环节。

### 3.1 训练机制与损失函数

训练过程遵循标准的监督学习范式，按以下循环迭代执行：

1. **前向传播**：模型根据输入（prompt）生成输出；
2. **损失计算**：将模型输出与目标答案比较，计算交叉熵损失（Cross-Entropy Loss）；
3. **反向传播**：根据损失计算梯度，调整模型参数；
4. **多轮迭代**：重复上述过程直至模型充分收敛。

**SFT 损失函数的特殊之处**：

在计算损失时，**仅对模型输出部分（即生成的回答 tokens）计算损失，而不对用户输入的 prompt 部分计算损失**。这意味着：

- 模型只需学习“如何正确回答”，无需记忆或复述用户的提问；
- 训练目标为**最大化目标回答序列的生成概率**，即标准的自回归语言建模目标；
- 实践中通过设置 `ignore_index`（通常为 -100）来屏蔽 prompt 部分的损失计算。

通过这一机制，模型逐步习得目标任务的**数据格式规范**、**回答风格特征**和**领域专有知识**。

### 3.2 训练方式选型

大模型训练面临显存占用高、速度慢、成本高三重工程挑战，目前主流的训练方式如下：

| 训练方式 | 核心原理 | 资源消耗 | 效果表现 |
|---------|---------|---------|---------|
| **全参数微调** | 更新全部模型参数 | 最高 | 最优（数据充足时） |
| **LoRA** | 冻结原模型，插入低秩适配器进行训练 | 低 | 多数常规任务接近全参，复杂推理任务仍有差距 |
| **QLoRA** | LoRA + 量化技术，进一步压缩显存 | 最低 | 接近 LoRA，但训练速度较慢 |

**选型建议**：

| 场景 | 推荐方式 | 理由 |
|------|---------|------|
| 数据量大（>10万条）、追求极致效果、硬件充足 | 全参数微调 | 充分释放模型全部参数的学习潜力 |
| 数据量中等、需快速实验迭代、需同时维护多个任务 | LoRA | 不同任务可切换不同的 adapter，存储和切换成本极低 |
| 显存严重受限（如消费级显卡）、需在有限硬件上完成训练 | QLoRA | 可在单张 24GB 显卡上微调 70B 级别模型 |

### 3.3 关键超参数参考

SFT 训练中，以下超参数对最终效果影响显著，建议作为初始配置参考：

| 超参数 | 典型值范围 | 说明 |
|-------|----------|------|
| 学习率（全参数微调） | 1e-5 ~ 5e-5 | 通常比预训练阶段小 1-2 个数量级 |
| 学习率（LoRA/QLoRA） | 1e-4 ~ 1e-3 | LoRA 适配器可采用较高学习率 |
| 批次大小（Batch Size） | 根据显存调整（通常 1-32） | 较大批次通常更稳定，但受显存限制 |
| 训练轮数（Epochs） | 1 ~ 3 | SFT 通常不宜过多，容易过拟合 |
| 学习率调度 | Cosine / Linear | 配合 Warm-up 使用 |
| Warm-up 比例 | 0 ~ 10% | 训练初期逐步提升学习率，有助于训练稳定性 |


## 4. 模型验证

模型验证是检验微调成效的最终关口——**训练损失下降不等于模型可用**，必须通过多维度的综合评估。

### 4.1 建立评估基线（Baseline）

在评估微调模型效果之前，应首先建立评估基线，以此衡量微调带来的真实增益：

| 基线类型 | 评估方式 | 目的 |
|---------|---------|------|
| **零样本基线（Zero-shot）** | 原始模型直接推理，不加任何示例 | 衡量微调带来了多少净提升 |
| **少样本基线（Few-shot）** | 在 prompt 中提供 2-5 个示例后推理 | 评估模型在不经微调时的上下文学习能力上限 |

> **实践要点**：微调模型的评估结果应与上述基线进行对比，而非仅看绝对值。若微调效果低于少样本基线，说明微调未达到预期效果，需重新审视数据质量、训练策略或超参数配置。若微调效果显著优于零样本基线但略低于少样本基线，则说明模型已学到了部分任务模式，但仍有优化空间。

### 4.2 验证维度

模型验证应从以下四个层面全面展开：

**维度一：训练损失与验证损失**
- 评估模型在训练集上的拟合程度及在未见数据上的泛化能力
- 关注损失曲线是否平滑下降，警惕训练损失下降但验证损失上升（过拟合信号）

**维度二：任务指标**
- 根据任务类型选择合适的定量评估指标（详见 4.3 节）
- 除总体指标外，建议按难度或类别细分评估，定位薄弱环节

**维度三：样例推理结果**
- 通过具体输入输出样例，直观判断模型回答质量
- 采用人工评估或自动评测相结合，重点关注指令遵循度、回答准确性和格式规范性

**维度四：实际任务效果**
- 在真实或模拟业务场景中进行端到端测试
- 收集用户反馈，验证模型的实际可用性和用户体验

### 4.3 按任务类型的评估指标参考

不同任务类型应选用不同的核心评估指标：

| 任务类型 | 推荐核心指标 | 补充说明 |
|---------|------------|---------|
| 文本分类、意图识别 | Accuracy、宏平均 F1 | 类别不平衡时重点关注 F1 而非 Accuracy |
| 摘要生成、对话生成 | ROUGE-L、BLEU、BERTScore | BERTScore 与人工评估相关性更高 |
| NL2SQL | 执行准确率（Execution Accuracy）、SQL 语法正确率 | 执行准确率比精确匹配更反映实际可用性 |
| RAG/知识库问答 | 答案正确率、引用召回率、Hallucination 率 | 需同时评估是否产生幻觉 |
| 多轮对话 | 对话连贯性、任务完成率、用户满意度 | 可借助 LLM-as-Judge 进行自动评估 |
| 结构化输出（JSON等） | 格式通过率、字段完整率 | 语法正确性是可用性的基本前提 |

### 4.4 常见问题诊断

通过系统验证，可以及早发现以下典型问题：

| 问题类型 | 典型表现 | 可能原因 | 改进方向 |
|---------|---------|---------|---------|
| 过拟合 | 训练损失持续下降，验证损失不降反升 | 数据量不足、轮数过多、模型过大 | 增加数据、减少轮数、引入正则化 |
| 欠拟合（指令跟随不足） | 模型未按指令执行、输出随机性强 | 数据质量差、学习率不当 | 优化数据格式、调整学习率 |
| 回答质量不稳定 | 相同类型问题输出波动大 | 训练数据多样性不足 | 扩充训练数据、增加数据覆盖 |
| 格式输出错误 | 未按要求输出 JSON/表格等格式 | 数据格式不一致 | 规范训练数据中的输出格式 |
| 领域知识未学到 | 专业问题回答错误或泛泛而谈 | 领域数据不足或质量低 | 补充高质量领域数据 |

### 4.5 验证的价值闭环

验证不仅是终点，更是下一轮迭代的起点。验证结果为以下后续工作提供直接依据：

- **数据优化**：补充薄弱场景样本、修正错误标注、平衡类别分布；
- **参数调整**：调整学习率、训练轮数、批次大小等超参数；
- **训练策略改进**：更换训练方式（如从 LoRA 切到全参微调）、调整模型规模。

验证驱动的迭代优化闭环如下：

> **微调训练 → 模型验证 → 问题诊断 → 数据/参数/策略优化 → 重新训练 → 再验证**
>
> 重复此循环，直至模型效果达到业务可接受标准。


## 本章核心要点

| 环节 | 核心要点 |
|------|---------|
| **模型选择** | 优先选用 Instruct Model，从 7B/14B 起步，按需升级；关注领域专用模型 |
| **数据准备** | 原始数据需经筛选→清洗→结构化→答案构造→格式转换五步处理，答案质量是上限 |
| **微调训练** | 根据硬件和数据量选择全参微调、LoRA 或 QLoRA；学习率 1e-5~5e-5（全参）或 1e-4~1e-3（LoRA），轮数 1-3 |
| **模型验证** | 先建立 Zero-shot/Few-shot 基线，再从训练损失、任务指标、样例推理、实际效果四维综合评估；指标需按任务类型选择；形成优化闭环 |
