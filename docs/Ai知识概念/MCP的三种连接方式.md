# MCP传输的三种方式

## 1. 概述
MCP（模型上下文协议）使用 JSON-RPC 格式编码消息，而**传输层（Transport）** 则定义了这些消息在客户端与服务器之间的实际传递方式。目前主流的方式有三种，其中 **stdio** 和 **Streamable HTTP** 是当前最核心、最常用的两种。

---

## 2. 三种传输方式概览

| 传输方式 | 核心定位 | 适用场景 | 当前状态 |
| :--- | :--- | :--- | :--- |
| **stdio** | 本地进程间通信，通过标准输入/输出交换数据 | 桌面应用、本地开发（如 Claude Desktop） | **推荐用于本地** |
| **HTTP + SSE** | 通过网络传输，使用 POST + SSE 双向通道 | —— | **已废弃**（2024-11-05 后不推荐） |
| **Streamable HTTP** | 单一 HTTP 端点，支持 POST + SSE 流式传输 | 云端部署、多客户端、分布式系统 | **推荐用于网络** |

---

## 3. 核心区别：stdio vs Streamable HTTP

这是你最需要关注的两者对比。用一个比喻来理解：

> **stdio** 是老板站在你工位旁派活，你干完一件他才派下一件（串行，排队）。  
> **Streamable HTTP** 是老板把所有工单都扔到前台，前台一次性全给你，你可以同时开干（并行，并发）。

### 3.1 对比表格

| 对比维度 | stdio | Streamable HTTP |
| :--- | :--- | :--- |
| **通信方式** | 标准输入（stdin）/ 标准输出（stdout） | 单一 HTTP 端点（POST + GET），支持 SSE 流式推送 |
| **网络依赖** | 无需网络，本地进程间通信 | 需要网络，支持跨机器、跨地域调用 |
| **并发能力** | **并发度为 1**（串行处理，同一时间只能处理一个请求） | **并发度为 5**（并行处理，同一时间最多处理 5 个请求） |
| **配置复杂度** | 极低，零配置 | 中等，需配置 HTTP 端点地址 |
| **典型场景** | Claude Desktop 本地集成、命令行工具 | 云端 AI 服务、多租户系统、实时流式响应 |

---

### 3.2 核心澄清：stdio ≠ 网络连接

**这是新人最容易踩的坑。** 很多人一听到“连接”就默认是网络连接，但 stdio 完全不是。

**关键认知**：
> **stdio 模式下，MCP 服务器不是“连上去”的，而是“被客户端生出来”的。**

- **stdio**：客户端（如 Claude Desktop）根据配置文件，**主动在你的电脑上启动一个子进程**（比如执行 `python mcp_server.py`）。客户端和这个子进程之间通过**标准输入（stdin）/ 标准输出（stdout）** 管道直接对话。**全程不走网络，没有 IP 地址，没有端口，没有 HTTP 请求。**
- **Streamable HTTP**：MCP 服务器是一个**独立运行的网络服务**（比如运行在 `https://api.example.com/mcp`）。客户端通过 **HTTP 客户端** 发送网络请求去调用它。**这才是你传统认知里的“连接”——有 IP、有端口、有 HTTP 请求。**

**一句话总结**：
> **stdio = 本地子进程通信（无网络）**  
> **Streamable HTTP = 远程网络服务调用（有网络）**

---

### 3.3 核心澄清：stdio 的 MCP 是“独立进程”，不是“第三方库”

另一个常见误区是：以为 stdio 方式下，MCP 就是一个可以 `import` 的第三方库（比如 `pip install mcp` 然后直接调用）。

**纠正**：
> **stdio 方式下的 MCP 是一个“独立运行的程序”，而不是一个“可供导入的代码库”。**

| 对比 | 普通第三方库（如 requests、pymysql） | stdio 模式的 MCP 服务器 |
| :--- | :--- | :--- |
| **形态** | 一个代码包，你在自己的代码里 `import` 后直接调用函数 | 一个**独立程序文件**（.py / .js / .exe），由客户端**作为子进程启动** |
| **谁启动它** | 你的代码里直接 `import`，没有“启动”这个概念 | 客户端（如 Claude Desktop）**执行命令把它启动为一个独立进程** |
| **通信方式** | 函数调用（在同一个进程的内存里传参） | 进程间通信（通过 stdin/stdout 管道） |
| **类比** | 你买了个计算器放桌上，随手拿起来按 | 你雇了个助理坐在工位旁，你喊一声他帮你算，算完把结果递给你 |

**实际配置示例**（Claude Desktop 的配置文件）：
```json
{
  "mcpServers": {
    "my-local-tools": {
      "command": "python",
      "args": ["/Users/yourname/mcp_server.py"]
    }
  }
}
```
这里的 `mcp_server.py` 是一个**独立的程序入口**，Claude Desktop 启动时会把它作为一个**子进程**拉起来，然后通过管道通信。它不是一个库，而是一个可运行的程序。

## 4. 核心概念澄清：并发度 ≠ 一次调用多个 API

### 4.1 每个“请求”对应什么？

**在 MCP 中，每一个独立的请求（Request）对应调用一个具体的 Tool（即一个后端 API）。**

- **正确理解**：`并发度 = 5` 表示 MCP 服务器**同一时间最多能并行处理 5 个独立的 Tool 调用**。这 5 个调用可以来自同一个用户的多个连续指令，也可以来自 5 个不同用户的各自请求。
- **错误理解**：不是说“一次请求里能塞进 5 个 API 一并调用”。如果想在一个用户指令里触发多个 Tool，那是 **AI 客户端（如 Claude）** 的编排逻辑（Tool Call）负责的，它会发起多次独立的 MCP 请求。

### 4.2 现实场景举例

假设一个 MCP 服务器暴露了 5 个 Tool（查员工、查预算、查项目、发邮件、生成报表）：

- **场景 A（单用户多请求）**：你问“查张三信息 + 查部门预算 + 查项目进度”，AI 后台同时发起 3 个并发请求，MCP 服务器并行处理，秒级返回。
- **场景 B（多用户同时用）**：5 个不同用户同时发起 5 个不同 Tool 调用，MCP 服务器并行处理 5 个请求，互不阻塞。
- **场景 C（并发占满排队）**：5 个耗时的“生成报表”正在处理，第 6 个“查员工”请求会排队等待，直到有槽位释放。

## 5. 如何选择？

| 你的需求 | 推荐方式 | 理由 |
| :--- | :--- | :--- |
| 本地开发、桌面应用、单用户、追求极简配置 | **stdio** | 零网络开销、延迟最低、配置最简单 |
| 云端部署、多用户接入、分布式架构、需要流式响应 | **Streamable HTTP** | 支持并行、跨网络、统一端点、便于扩展 |
| 第三方提供的是 URL 地址（如 `https://xxx.com/mcp`） | **Streamable HTTP** | 远程服务只能用 HTTP 访问，stdio 无法跨机器 |

> ⚠️ **注意**：**HTTP + SSE** 方式已在 2024-11-05 协议版本后被废弃，新项目请直接使用 Streamable HTTP。

---

## 6. 总结

- **stdio**：本地神器，极致简单，串行处理（并发度=1）。**MCP 是本地独立进程，不是库，不走网络。**
- **Streamable HTTP**：云端利器，统一端点，并行处理（并发度=5）。**MCP 是远程网络服务，通过 HTTP 调用。**
- **每个请求 = 调用一个 Tool（API）**，并发度指的是“同时能处理多少个这样的请求”，而不是“一个请求里能塞多少个 API”。
- **关键判断**：拿到的是本地程序文件 → 用 stdio；拿到的是 URL 地址 → 用 Streamable HTTP。
