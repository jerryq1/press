# A2A（Agent-to-Agent）

## 一、一句话理解

> **A2A 是让不同的 AI Agent 之间能够互相“认识”和“对话”的开放协议。**

如果说 Tool 是 Agent 的“手”，MCP 是连接工具的“神经”，那 **A2A 是 Agent 之间的“语言”**——让一个 Agent 能找另一个 Agent 帮忙干活。

---

## 二、生活比喻 

### 没有 A2A 的世界：
> 你请了三个助手：一个负责订机票，一个负责订酒店，一个负责查天气。但三个人各说各的语言，不会互相沟通。你想去旅游，得自己给 A 说“订机票”，拿到结果后告诉 B“订酒店”，再告诉 C“查天气”——你成了**人肉传话筒**。

### 有 A2A 的世界：
> 你只对“总管家”说一句：“帮我安排一趟去三亚的旅行。”总管家自动找机票助手、酒店助手、天气助手，它们之间互相沟通、同步信息，最后给你一个完整的方案。**你只需要说一次话。**

### 餐厅协作比喻：
> **游客 Agent** 想吃饭。
>
> **服务员 Agent**（通过 A2A）和游客沟通，记录“南昌炒粉，微辣，多放葱花”。
>
> 服务员通过 **A2A** 把订单发给**厨师 Agent**。
>
> 厨师收到订单后，通过 **MCP** 从食材库拿米粉、辣椒、葱花，调用炉灶、锅铲等工具炒菜。
>
> 炒好了，厨师通过 **A2A** 通知服务员，服务员端给游客。

**A2A 负责“人与人之间的沟通”，MCP 负责“人怎么用工具”。**

## 三、官方定义

> **A2A（Agent2Agent Protocol）** 是由 Google 于 2025 年 4 月发起、现由 Linux 基金会托管的**开放协议**，旨在实现不同平台、不同框架构建的 AI Agent 之间的**互操作与协作**。

**核心目标：** 让 Agent 之间可以：
- 发现对方的能力
- 协商任务分配
- 交换上下文信息
- 协同完成复杂任务

**生态现状：**
- **50+ 合作伙伴**：Atlassian、Salesforce、SAP、LangChain、MongoDB 等
- **托管方**：Linux 基金会（2025 年 6 月）
- **当前缺席**：OpenAI、Anthropic（尚未支持）

## 四、核心架构

| 组件 | 作用 | 生活类比 |
|------|------|----------|
| **Agent Card（智能体名片）** | JSON 格式的能力描述文件，Agent 用它“自我介绍” | 简历/LinkedIn 主页 |
| **A2A Client** | 发起任务的 Agent（请求方） | 项目经理 |
| **A2A Server** | 执行任务的 Agent（接收方） | 具体干活的员工 |
| **Task（任务）** | 有状态的工作单元，有唯一 ID 和生命周期 | 工单/任务卡 |
| **Message（消息）** | Agent 之间传递的沟通内容 | 邮件/微信消息 |
| **Artifact（工件）** | 任务执行产出的结果 | 交付物（文档、图片等） |

## 五、工作流程

```
┌─────────────────────────────────────────────────────────────┐
│  Step 1: 发现（Discovery）                                  │
│  客户端 Agent 获取远程 Agent 的 "Agent Card"（能力名片）      │
│  判断对方能不能干这个活                                        │
│                           ↓                                  │
│  Step 2: 认证（Authentication）                             │
│  双方确认身份，建立安全连接                                    │
│                           ↓                                  │
│  Step 3: 通信（Communication）                              │
│  客户端发送 Task → 远程 Agent 执行 → 返回 Message/Artifact   │
│  支持长时间任务（异步通知、SSE 流式传输）                      │
└─────────────────────────────────────────────────────────────┘
```

## 六、A2A vs MCP

这是最容易混淆的地方，用一个表格说清楚：

| 维度 | **MCP（模型上下文协议）** | **A2A（Agent间协议）** |
|------|--------------------------|------------------------|
| **解决什么问题** | Agent ↔️ 工具/数据 | Agent ↔️ Agent |
| **关系类型** | 上下级（调用关系） | 平级（协作关系） |
| **交互方式** | 结构化的函数调用 | 自然语言 + 任务协商 |
| **生活类比** | 修理工用扳手、螺丝刀 | 项目经理和修理工沟通 |
| **一句话** | “怎么用工具” | “怎么找帮手” |

**官方态度：** A2A ❤️ MCP —— 两者是**互补关系**，不是竞争关系。

## 七、A2A在实际项目中的定位 ⭐核心章节

### 7.1 直接回答：不是核心，但很重要

A2A 在当下实际项目中的定位是 **“基础设施层的补充协议”**，而不是 **“Agent 产品的核心”**。

### 7.2 实际项目中Agent产品的核心优先级

| 优先级 | 组件 | 占比（估算） | 为什么核心 |
|--------|------|--------------|------------|
| **1** | **业务逻辑 + Prompt 工程** | 40% | 决定了 Agent 能不能正确理解任务 |
| **2** | **单个 Agent 的 Tool 调用** | 25% | 90% 的实际任务靠 1 个 Agent + 几个 Tool 完成 |
| **3** | **记忆管理（Memory）** | 15% | 对话连贯性、长期记忆 |
| **4** | **评估与监控** | 10% | 生产环境必备，保证质量和成本 |
| **5** | **多 Agent 编排（含 A2A）** | 5-10% | 复杂场景才需要 |

**结论：A2A 排在第 5 位，不是日常核心，但特定场景必不可少。**

### 7.3 A2A的真正价值

不是让每个 Agent 项目都用它，而是：

#### 1. 解决“最后一公里”的集成问题

```
没有 A2A 的世界：
你做了一个很牛的 Agent，但别人想调用它？
→ 需要为每个调用方单独写接口、做认证、处理异步

有 A2A 的世界：
你发布一个 Agent Card（能力名片）
→ 任何支持 A2A 的 Client 都能自动发现和调用
```

#### 2. 生态层面，而非项目层面

| 角色 | A2A 的价值 |
|------|------------|
| **Agent 开发者** | 不用重复造“集成轮子”，专注业务逻辑 |
| **平台方** | 可以聚合第三方 Agent，形成生态 |
| **企业 IT** | 内部多个 Agent 系统可以标准化互通 |

### 7.4 真实项目的核心工作清单

#### 阶段一：MVP（最小可行产品）
- [ ] 选一个场景（如“智能客服”）
- [ ] 写 Prompt，调 LLM
- [ ] 接入 2-3 个 Tool（查订单、查商品）
- [ ] 处理好错误和重试

#### 阶段二：生产化
- [ ] 加记忆（短期：会话历史；长期：用户偏好）
- [ ] 加评估（准确率、召回率、Token 成本）
- [ ] 加安全护栏（内容过滤、权限控制）

#### 阶段三：规模化
- [ ] 拆分成多 Agent（如果需要）
- [ ] 做 Agent 间的编排（可以用 A2A，也可以用更简单的方案）
- [ ] 加缓存、降级、熔断

**A2A 只在阶段三出现，而且只是“多种实现方式之一”。**

### 7.5 务实的建议

| 情况 | 对 A2A 的态度 |
|------|----------------|
| 刚入门，做学习项目 | **先不管**，把单 Agent + Tool 做熟 |
| 做公司内部工具 | **大概率不需要**，直接写代码让 Agent 互调更简单 |
| 做平台/产品，要对接外部 Agent | **值得关注**，A2A 可能是未来的标准 |
| 做开源 Agent 框架 | **可以支持**，但不是优先功能 |

## 八、什么时候需要A2A？

### ❌ 大多数情况（80%+ 的项目）不需要 A2A

| 场景 | 是否需 A2A | 实际方案 |
|------|------------|----------|
| 客服机器人 | 否 | 单 Agent + 知识库检索 |
| 代码助手 | 否 | 单 Agent + 代码执行 Tool |
| 数据分析 | 否 | 单 Agent + SQL/Python Tool |
| 个人助理 | 否 | 单 Agent + 日历/邮件/天气 Tool |

**这些场景下，A2A 是“过度设计”。**

### ✅ 需要 A2A 的场景（少数但重要）

| 场景 | 为什么需要 A2A |
|------|----------------|
| **跨部门协作** | 销售 Agent 需要找库存 Agent 确认库存 |
| **异构系统集成** | 不同公司/团队开发的 Agent 需要互操作 |
| **长时间异步任务** | 一个 Agent 发起，另一个后台执行，完成后通知 |
| **专家 Agent 市场** | 动态发现和调用第三方 Agent 能力 |

**类比：** 开一家小餐馆不需要“行业协作标准”，但做 Uber Eats 这样的聚合平台，就需要标准协议让各家餐厅对接。

## 九、完整知识框架串联

```
                    ┌─────────────────────────────────────┐
                    │              Agent 生态栈            │
                    ├─────────────────────────────────────┤
                    │  A2A 协议（Agent ↔ Agent 协作层）     │
                    ├─────────────────────────────────────┤
                    │  MCP 协议（Agent ↔ Tool 连接层）     │
                    ├─────────────────────────────────────┤
                    │  Function Calling（模型 ↔ 函数层）    │
                    └─────────────────────────────────────┘
```

### 完整的一句话总结：

> **Tool 是手，MCP 是连接手的神经，Agent 是大脑，A2A 是大脑之间的语言。**

### 核心洞察：

- **做一把好椅子** → 核心是设计、木材、舒适度，不是“这椅子符合人体工学国际标准”
- **做 Agent 产品** → 核心是准确、好用、成本可控，不是“支持 A2A 协议”

**保持清醒：工具协议是手段，解决问题是目的。**

## 十、快速记忆卡

| 概念 | 类比 | 一句话 |
|------|------|--------|
| **Tool** | 螺丝刀 | 能力的封装 |
| **Agent** | 工匠 | 决策者，知道怎么用工具 |
| **MCP** | 工具接口标准 | 让 Agent 能连接任何工具 |
| **A2A** | 工匠之间的语言 | 让 Agent 能找其他 Agent 帮忙 |

### A2A 定位速记：

> **A2A 是 Agent 生态的“USB-C 接口标准”——重要，但不是你产品的核心功能。核心永远是“你的 Agent 能不能帮用户解决实际问题”。**
