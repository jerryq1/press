# 数据智能体：元知识构建系统架构(实体类)

## 一、整体架构概览

本项目采用**多存储异构架构**，根据不同数据特性选择最合适的存储引擎：

| 存储系统 | 存储内容 | 选型理由 |
|---------|---------|---------|
| MySQL (Meta库) | 表/列/指标的结构化元数据 | 强一致性、支持复杂关联查询 |
| MySQL (DW库) | 数据仓库原始数据 | 模拟真实业务数据源 |
| Qdrant | 列/指标的向量嵌入 | 专为向量相似度搜索优化 |
| Elasticsearch | 数据值全文检索 | 强大的分词与搜索能力 |

**生活比喻**：就像家庭收纳——重要文件放保险柜(MySQL)，相册放展示架(Qdrant找相似)，日记放抽屉方便翻查(ES全文检索)。


## 二、核心业务实体

### 2.1 什么是业务实体

**官方解释**：业务实体是纯净的业务对象，作为应用上层组件进行读写操作时的标准参数类型和返回值类型，隔离上层业务与底层存储差异。

**生活比喻**：业务实体=身份证（任何场合都能代表你），数据库模型=工牌（只在公司有用）。你不能拿工牌去银行办业务，同理业务逻辑只认业务实体。

### 2.2 为什么不直接使用数据库结构

直接使用数据库模型会导致三个问题：

| 问题 | 说明 |
|------|------|
| **技术锁定** | 业务代码直接依赖SQLAlchemy/MySQL，换数据库要改所有文件 |
| **存储细节污染** | 数据库字段（created_at、is_deleted）对业务无意义却会侵入代码 |
| **多存储困境** | 同一业务对象存在3种存储，需要3种不同模型，业务层无法统一处理 |

**核心原则**：业务实体是业务的语言，数据库模型是存储的技术。不要让技术词汇污染业务对话。

### 2.3 业务实体定义

本项目定义的业务实体有：TableInfo、ColumnInfo、MetricInfo、ColumnMetric、ValueInfo。

```python
# 示例：TableInfo 核心结构
@dataclass
class TableInfo:
    id: str
    name: str
    role: str        # fact/dimension
    description: str

@dataclass
class ColumnInfo:
    id: str
    name: str
    type: str        # int/string/date
    role: str        # dimension/metric/time
    examples: list
    description: str
    alias: list[str] # 如["销售额","GMV"]
    table_id: str
```


## 三、Repository模式实现

### 3.1 什么是Repository模式

**官方解释**：数据映射层，隔离业务逻辑与数据源细节。

**生活比喻**：图书馆前台——你只需告诉前台"我要《三体》"，不需要知道书在几楼几架。

### 3.2 Mapper双向转换

Mapper负责SQLAlchemy实体类与业务实体类之间的类型转换。

```python
class TableInfoMapper:
    @staticmethod
    def to_entity(model: TableInfoMySQL) -> TableInfo:
        return TableInfo(
            id=model.id,
            name=model.name,
            role=model.role,
            description=model.description
        )
    
    @staticmethod
    def to_model(entity: TableInfo) -> TableInfoMySQL:
        return TableInfoMySQL(**asdict(entity))
```

**Mapper的价值**：当数据库结构变化时，只需修改Mapper中的转换逻辑，业务层代码完全不受影响。

### 3.3 MySQL Repository示例

```python
class MetaMySQLRepository:
    def __init__(self, session: AsyncSession):
        self.session = session
    
    async def save_table_infos(self, table_infos: list[TableInfo]):
        models = [TableInfoMapper.to_model(t) for t in table_infos]
        self.session.add_all(models)
```

## 五、关键设计模式

### 5.1 依赖注入

```python
# 推荐：依赖注入
class MetaRepository:
    def __init__(self, session: AsyncSession):  # 外部传入
        self.session = session

# 不推荐：硬依赖
class MetaRepository:
    def __init__(self):
        self.session = create_session()  # 紧耦合，难以测试
```

### 5.2 异步批量操作

```python
async def upsert(self, items, batch_size=20):
    for i in range(0, len(items), batch_size):
        batch = items[i:i+batch_size]
        await self._do_batch(batch)  # 分批避免内存爆炸
```

**生活比喻**：搬家时不一次搬100本书（太重），也不跑100趟（太慢），每趟搬20本刚刚好。


## 六、事务边界管理

```python
# 正确：显式控制事务边界
async with self.meta_mysql_repository.session.begin():
    await self.meta_mysql_repository.save_metric_infos(metric_infos)
    await self.meta_mysql_repository.save_column_metrics(column_metrics)
# 任一失败，全部回滚

# 错误：分散提交可能导致数据不一致
await self.meta_mysql_repository.save_metric_infos(metric_infos)
await self.session.commit()  # 第一次提交
await self.meta_mysql_repository.save_column_metrics(column_metrics)  # 失败则数据不一致
```


## 七、数据库变更的影响范围

### 7.1 核心结论

**问**：数据库结构改了或换了数据库，我需要修改转换方法吗？

**答**：是的，但这是**代价最小、影响范围最小**的方案。

### 7.2 影响对比

| 变更场景 | 不分层（直接依赖DB模型） | 分层（使用业务实体） |
|---------|------------------------|---------------------|
| MySQL→PostgreSQL | 修改所有业务代码（几十个文件） | 只改Repository层（1-2个文件） |
| 新增数据库字段 | 业务代码可能被动修改 | Mapper忽略或适配，业务不变 |
| 删除字段 | 所有使用处报错 | 只在Mapper处理 |
| 改变字段类型 | 到处修改转换逻辑 | 集中在Mapper转换 |

### 7.3 各场景下的Mapper处理

```python
# 场景1：数据库新增字段（业务不需要）
# Mapper忽略即可，业务实体不变

# 场景2：数据库字段改名
username = model.user_name  # Mapper中做映射

# 场景3：数据库类型变更（JSON→字符串）
name = model.name.get("zh") if isinstance(model.name, dict) else model.name

# 场景4：换数据库
class MetaPostgreSQLRepository:  # 新Repository
    def get(self, id): 
        model = session.query(TableInfoPG).get(id)  # 改SQL语法
        return TableInfoMapper.to_entity(model)  # Mapper复用！
```

### 7.4 是否需要分层的判断标准

```
简单脚本（1个存储，简单映射） → 不分层，直接干
复杂系统（多存储，复杂转换） → 分层，值得付出映射成本
```

**本项目属于后者**：使用了MySQL、Qdrant、ES三个存储，还有向量、全文索引等复杂特性。

## 九、核心收益总结

| 收益 | 说明 |
|------|------|
| **更换存储零成本** | MySQL换PostgreSQL，只改Repository和Mapper |
| **数据库结构变化影响小** | 只需修改Mapper转换逻辑，业务层无感知 |
| **单元测试容易** | Mock业务实体比Mock数据库连接简单100倍 |
| **多存储统一操作** | 同一个业务实体可同时写MySQL、Qdrant、ES |

**一句话记忆**：业务实体是业务的语言，数据库模型是存储的技术。你只需要关注业务实体，数据库的变化交给Repository和Mapper处理。
