# RAG 级联系统双轨评测架构指南

> **报告摘要**：本文档完整呈现了生产级 RAG Agent 评测体系的设计思路与落地实践——自研节点诊断引擎专注于 **Ragas 无法替代的白盒指标**（实体识别准确率、RRF 粗排召回率），而 **Rerank 截断质量**（误杀率/噪声消除率）因强依赖 `gold_chunk_ids` 精准标注，已移交 Ragas 的 `Context Precision` 语义级评估。两套引擎形成了一套兼顾**工程调优效率**与**行业标准对齐**的双轨评测最佳实践。文档同时收录了评测体系建设过程中的**关键踩坑经验**与对应的解决方案。


## 一、 为什么需要双轨评测体系？

### 1.1 单用 Ragas 的痛点

在早期迭代中，我们直接用 Ragas 做端到端评测，遇到了三个核心痛点：

| 痛点        | 具体表现 | 根因 |
|:----------|:---|:---|
| **时间成本高** | 跑 30 条测试集消耗数万 Token，耗时数分钟 | Faithfulness 需将每个答案拆成陈述句逐条调用 LLM 判断 |
| **不可定位**  | Context Precision 得 0.92，不知道是"召回少了"还是"重排误杀了" | Ragas 是黑盒端到端评估，不感知中间节点状态 |

### 1.2 自研诊断脚本的定位

我们基于 LangGraph 的 State 可观测性，自研了节点诊断引擎 `evaluate_rag.py`：

- **节点级白盒诊断**：能精确指出"实体识别坏了"还是"RRF 召不回文档了"
- **极速零成本**：大部分指标用确定性硬计算，30 条 Case 几秒跑完，零 Token 消耗
- **100% 可复现**：不受 LLM 随机性影响，适合 CI/CD 回归测试

### 1.3 指标职责分工（核心设计决策）

| 指标类别 | 负责引擎 | 理由 |
|:---|:---|:---|
| **实体识别准确率** | 自研脚本 | Ragas 不感知 LangGraph 节点内部状态 |
| **RRF 粗排召回率** | 自研脚本 | Ragas 不检测粗排阶段是否召回了文档 |
| **Rerank 截断质量** | Ragas (Context Precision) | 原误杀率/噪声消除率强依赖 `gold_chunk_ids` 精准标注，若标注为实体全量切片则严重失真，改用语义级 LLM 裁判更客观 |
| **Faithfulness / Relevance** | 双轨交叉验证 | 自研脚本与 Ragas 同时计算，对比验证 |

**最终策略**：两者不是替代关系，而是**分工协作、双轨并行**。


## 二、 评测基准与环境

所有评测均在完全相同的条件下运行：

| 项目 | 说明 |
|:---|:---|
| **黄金测试集** | `app/evaluation/test_eval_dataset.json`（从 Milvus 黄金切片反向生成真实业务 Query、标准实体 `item_names` 与标准文档 `gold_chunk_ids`） |
| **RAG 链路** | LangGraph 级联图（问题重写 → 实体绑定 → BGE-M3 + HyDE + MCP 多路召回 → RRF 融合 → bge-reranker-v2-m3 精排与 25% 相对断崖截断 → LLM 生成） |
| **裁判 LLM** | 通义百炼 / DashScope Qwen（通过 `get_llm_client()` 统一装配） |

**⚠️ 关键链路特征**：当**实体识别节点失败**时（`item_names` 为空或无法匹配黄金实体），系统**直接短路返回澄清/拒绝话术，不会进入后续的 RRF 召回、Rerank 截断和 LLM 生成环节**。这一特征对评测脚本的设计有重大影响（详见第六章）。

### 3.2 核心指标计算逻辑详解

#### 指标 1：实体对齐准确率（Entity Alignment Accuracy）—— 全量用例

```python
actual_entities = result_state.get("item_names", [])  # 系统提取的实体
gold_entities = case.get("gold_entities", [])         # 标准实体

entity_hit = set(actual_entities) & set(gold_entities)
if gold_entities:
    entity_accuracy = len(entity_hit) / len(gold_entities)
else:
    entity_accuracy = 1.0 if not actual_entities else 0.0
```

**业务含义**：衡量系统能否将用户口语化/模糊表述（如"那个红色的""上一款"）准确映射为标准产品实体名。**这是多轮对话和意图理解的核心能力指标。**

**统计口径**：在全量用例上计算，反映系统真实的意图理解能力。

#### 指标 2：RRF 粗排召回率（RRF Recall@10）—— 仅有效且有标注用例

```python
rrf_chunks = result_state.get("rrf_chunks", [])       # RRF 融合后的 Top 10
rrf_ids = {str(c.get("chunk_id")) for c in rrf_chunks}
gold_chunk_ids = case.get("gold_chunk_ids", [])       # 黄金标准切片 ID

if gold_chunk_ids:
    rrf_recall = 1.0 if (gold_chunk_ids & rrf_ids) else 0.0
```

**业务含义**：**硬指标**——判断黄金切片是否进入了 RRF 粗排的 Top 10。如果为 0，说明多路召回（BGE-M3 + HyDE + MCP）本身就没找到正确文档，后续精排无论多强都无法补救。**这是整个检索链路的"底线指标"。**

**统计口径**：仅在**有效用例**且**有 `gold_chunk_ids` 标注**的用例上计算。`web_search` / `options_candidate` 类型用例无黄金切片标注，自动跳过此项考核。

#### 指标 3 & 4：Faithfulness 与 Relevance（LLM-as-Judge）—— 仅有效用例

```python
faith_score, faith_reason = llm_evaluate_faithfulness(llm_judge, contexts, actual_answer)
rel_score, rel_reason = llm_evaluate_relevance(llm_judge, query, actual_answer)
```

**设计要点**：两套评测用**同一个 Qwen 客户端**作为裁判，确保与 Ragas 的对比基准一致。Prompt 设计上强制要求返回 JSON 格式并附带推理理由，便于人工回溯裁判逻辑。

**统计口径**：仅在**有效用例**上计算，避免被拦截 Case 的澄清话术拉低全局均值。

### 3.3 已移除指标及原因

| 原指标 | 移除原因 | 替代方案 |
|:---|:---|:---|
| **Rerank 黄金切片误杀率** | 强依赖 `gold_chunk_ids` 精准标注。若 `gold_chunk_ids` 仅为实体全量切片而非 Rerank 截断维度的标准答案，则指标严重失真 | Ragas `Context Precision`（语义级 LLM 裁判，不依赖硬 ID 标注） |
| **动态断崖去噪率** | 同上，噪声判定依赖 `gold_chunk_ids` 的完整性 | Ragas `Context Precision` 综合评估排序质量 |


## 四、 横向打分对比结果

| 评估维度 | 自研脚本实测 | Ragas 评估 | 异同剖析 |
|:---|:---|:---|:---|
| **实体识别 & 绑定** | **80.0%** | 不支持 | 自研能捕获置信度中等时的路由打断与交互澄清状态 |
| **RRF 多路召回率** | **80.0%** | Context Recall: **0.95** | 自研看绝对 `chunk_id` 碰撞；Ragas 用 LLM 判断语义重合度 |
| **Rerank 截断质量** | 已移除 | Context Precision: **0.92** | 自研原误杀率/去噪率强依赖标注质量，移交 Ragas 语义级评估 |
| **答案忠实度** | **0.99** | Faithfulness: **0.96** | 两者一致极高，证明系统无事实性幻觉 |
| **答案相关性** | **0.97** | Answer Relevance: **0.94** | Ragas 算向量余弦相似度；自研比对核心意图 |


## 五、 两套引擎优劣势深度对比

### 自研诊断脚本 (`evaluate_rag.py`)

| 优势 | 劣势 |
|:---|:---|
| ✅ 节点级白盒诊断，精准定位"实体识别"和"粗排召回"环节 | ❌ 依赖黄金测试集标注 |
| ✅ 极速（秒级）+ 零额外 Token 成本 | ❌ 指标名称非通用 Benchmark 格式 |
| ✅ 100% 确定性，适合 CI/CD 回归测试 | ❌ Rerank 截断质量无法可靠评估（依赖标注精度） |

### Ragas 评估框架 (`evaluate_ragas.py`)

| 优势 | 劣势 |
|:---|:---|
| ✅ 业内标准 Benchmark，对外说服力强 | ❌ 高 Token 消耗 + 慢（分钟级） |
| ✅ 黑盒端到端评估，无需标注 `gold_chunk_ids` | ❌ 无法指导中间节点调参 |
| ✅ Context Precision 语义级评估 Rerank 质量，不依赖硬标注 | ❌ LLM-as-Judge 存在随机波动 |


## 六、 【关键踩坑经验】测试集质量管控与级联失效防护

### 6.1 问题本质：系统链路特征决定了"坏 Case"必然污染所有指标

本系统的 RAG 链路有一个**关键特征**：

> **当实体识别失败时（`item_names` 为空或无法匹配任何黄金实体），LangGraph 工作流会直接短路返回澄清/拒绝话术，不会进入后续的 RRF 召回、Rerank 截断和 LLM 生成环节。**

这个设计本身是合理的（快速失败、节省资源），但它对**评测脚本**提出了特殊要求：

#### 当"坏 Case"进入评测时，会发生什么？

```
┌─────────────────────────────────────────────────────────────────────────────┐
│  一条"坏 Case"的污染路径                                                    │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  用户 Query: "那个红色的多少钱"                                              │
│  Gold 实体: ["Product_A"]                                                   │
│  Gold Chunk ID: ["chunk_001"]                                               │
│                                                                             │
│  ═════════════════════════════════════════════════════════════════════════ │
│                                                                             │
│  ① 实体识别节点：item_names = []  ❌ 识别失败                               │
│                                                                             │
│  ② 系统判断：item_names 为空 → 触发澄清流程                                 │
│     ↓                                                                       │
│  ③ 工作流直接返回（短路），不进入 RRF/Rerank/LLM                            │
│     ↓                                                                       │
│  ④ State 中：                                                               │
│     - rrf_chunks = []        ← 空                                          │
│     - reranked_docs = []     ← 空                                          │
│     - answer = "您想查询哪个产品呢？请提供具体型号。"                        │
│                                                                             │
│  ═════════════════════════════════════════════════════════════════════════ │
│                                                                             │
│  ⑤ 指标计算（灾难性结果）：                                                  │
│                                                                             │
│     实体准确率 = 0/1 = 0%        ← 拉低全局均值                            │
│     RRF Recall = 1.0 if (gold_chunk_ids & 空集) else 0.0 = 0%  ← 拉低全局 │
│     Faithfulness: 评估"澄清话术"vs"空上下文" → 得分极低（~0.1）  ← 拉低   │
│     Relevance: 评估"澄清话术"vs"用户提问" → 得分极低（~0.2）   ← 拉低    │
│                                                                             │
│  ═════════════════════════════════════════════════════════════════════════ │
│                                                                             │
│  最终结果：一条"坏 Case"拖垮了所有平均指标，评测报告完全失真                 │
│  且无法区分是"系统检索能力差"还是"测试集本身就不该被评测"                    │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 6.2 真实业务场景举例

以下类型的 Query 极易触发"实体识别失败→直接拦截"：

| 类型 | 示例 | 为什么失败 |
|:---|:---|:---|
| **指代不明** | "那个红色的多少钱" | 没有上下文指代对象，"那个红色的"无法映射到产品实体 |
| **口语化缩写** | "P15 咋样" | 实体映射表未覆盖 "P15" → "Product_Pro_15" |
| **超纲实体** | "iPhone 15 支持 WiFi 7 吗" | 知识库里没有 iPhone 15 的任何文档 |
| **跨领域问题** | "今天天气怎么样" | RAG 系统仅做产品知识库问答，天气超出能力边界 |
| **语义模糊** | "你们最好的产品是什么" | "最好的"是主观描述，无法映射到具体产品实体 |

### 6.3 解决方案：测试集有效性预检门禁

在评测主循环中，通过 `validate_case_entity_recognition()` 函数识别哪些 Case 会被系统拦截：

```python
def validate_case_entity_recognition(case: dict, result_state: dict) -> tuple:
    """
    校验当前测试用例的主体/实体识别是否成功，判定其是否具备进入下游检索与生成链路的有效资格。
    
    原理：在 LangGraph RAG 级联图中，若实体识别失败，工作流会直接短路拦截返回，
    不会执行 RRF 召回与 Rerank 精排。因此需要将此类用例拦截，剔除其下游指标计算。
    """
    gold_entities = case.get("gold_entities", [])
    actual_entities = result_state.get("item_names", [])
    options = result_state.get("options", [])
    
    hit_set = set(actual_entities) & set(gold_entities)
    
    # 门禁 1：黄金实体必须非空
    if not gold_entities:
        if options:
            return False, "触发了二义性澄清流程 (options)，系统未进入下游检索"
        return True, "黄金实体未标注，默认视为成功"
        
    # 门禁 2：系统必须至少识别出一个黄金实体（核心门禁）
    if not hit_set:
        return False, f"主体识别失败 (系统识别: {actual_entities}，黄金标准: {gold_entities})，导致链路拦截"
        
    # 门禁 3：系统不能触发澄清流程
    if options:
        return False, f"触发了二义性澄清选项 (options: {options})，未能直接进入检索"
        
    return True, "主体识别成功，正常进入检索与生成链路"
```

### 6.6 踩坑经验总结

| 教训 | 根因 | 解决方案 | 状态 |
|:---|:---|:---|:---|
| **"坏 Case"导致所有指标崩塌** | 实体识别失败→系统拦截→下游数据全空 | `validate_case_entity_recognition()` 预检过滤 | ✅ 已集成 |
| **指标低分不代表系统差** | 测试集质量不可控 | 报告中标注有效用例率 | ✅ 已集成 |
| **Faithfulness 被澄清话术拉低** | 拦截 Case 的 answer 不是真实回答 | 仅对有效用例计算 E2E 指标 | ✅ 已集成 |
| **Rerank 指标依赖标注精度失效** | `gold_chunk_ids` 标注为实体全量切片而非截断维度标准答案 | 移交 Ragas Context Precision | ✅ 已调整 |

**核心认知**：

> **评测脚本本身也是被测系统的一部分。** 当系统有"快速失败"机制时，评测脚本必须理解并适配这一机制，而不是机械地计算所有 Case 的平均值。
>
> **"坏 Case"的 0 分不代表系统检索能力差，只代表"这条 Case 本来就不该被评测"。** 区分这两者，是评测体系设计的基本功。


## 七、 结论与最佳实践

### 💡 结论 1：指标职责分工是核心设计决策

| 指标 | 负责引擎 | 核心理由 |
|:---|:---|:---|
| 实体识别准确率 | 自研 | Ragas 不感知 LangGraph 节点状态 |
| RRF 粗排召回率 | 自研 | Ragas 不检测粗排阶段 |
| Rerank 截断质量 | Ragas Context Precision | 不依赖 `gold_chunk_ids` 硬标注，语义级评估更客观 |
| Faithfulness / Relevance | 双轨交叉验证 | 相互校验，确保可信度 |

### 💡 结论 2：评测体系必须适配系统链路特征

> 当系统有"实体识别失败→直接拦截"的快速失败机制时，评测脚本必须理解这一机制，并在指标体系上做出相应设计——**区分"被测系统的问题"和"测试集本身的问题"**。

### 💡 结论 3：测试集质量是评测体系的基石

所有指标的有效性，都建立在测试集质量可控的前提下。**评测脚本的第一道防线，是验证测试集本身是否有效。**

### 💡 结论 4：生产级双轨策略

| 场景 | 使用工具 | 职责 |
|:---|:---|:---|
| **日常开发/调参** | 自研脚本 | 监控实体识别 + RRF 召回，精准定位问题节点 |
| **阶段性汇报/对外** | Ragas | 输出 Context Precision 等标准指标，对齐业界 |

```
                      ┌──────────────────────────────────────────────┐
                      │    双轨评测架构 (Dual-Track Evaluation)      │
                      └──────────────────────┬───────────────────────┘
                                             │
                       ┌─────────────────────┴─────────────────────┐
                       ▼                                           ▼
      【自研诊断脚本 (evaluate_rag.py)】              【Ragas 评估框架 (evaluate_ragas.py)】
                       │                                           │
         - 实体识别准确率（全量）                     - Context Precision（Rerank 质量）
         - RRF 粗排召回率（有效+有标注）              - Faithfulness（交叉验证）
         - Faithfulness / Relevance（交叉验证）      - Answer Relevance（交叉验证）
         - 测试集有效性预检（质量门禁）
```


## 附录 A：核心指标映射关系

| Ragas 指标 | 对应 RAG 环节 | 自研脚本覆盖 | 说明 |
|:---|:---|:---|:---|
| Context Recall | 检索环节 | ✅ RRF 粗排召回率 | 自研看粗排 ID 碰撞；Ragas 看语义重合度 |
| Context Precision | 重排/截断环节 | ❌ 已移除 | 自研原指标依赖标注精度，移交 Ragas |
| Faithfulness | 生成环节 | ✅ 双轨交叉验证 | 双方同时计算，对比验证 |
| Answer Relevance | 意图理解/生成 | ✅ 实体识别 + LLM 相关性 | 自研拆分为节点级+端到端 |


## 附录 B：快速故障排查指南

| 现象 | 可能根因 | 验证方法 |
|:---|:---|:---|
| **用例有效率低** | 测试集中混入了大量"坏 Case" | 查看报告中的"被排除用例列表"，人工审核这些 Query 是否合理 |
| **实体准确率低** | 实体绑定 Prompt 失效或口语化表达未覆盖 | 检查 `item_names` 输出，补充 Few-shot 示例 |
| **RRF 召回率低** | 多路召回策略问题（HyDE 失效 / MCP 超时） | 检查 `rrf_chunks` 是否为空，调整检索权重 |
| **Faithfulness 低但 Context Precision 高** | 上下文相关但 LLM 生成时产生了幻觉 | 检查生成 Prompt 是否要求严格基于上下文 |
| **Relevance 低** | 答非所问，意图理解或生成 Prompt 问题 | 检查 `item_names` 是否正确映射到用户意图 |
| **Context Precision 低** | Rerank 排序质量差，黄金文档排位靠后 | 运行 `evaluate_ragas.py` 查看详细排序分析 |
| **所有检索指标同时暴跌** | 测试集污染，大量 Case 被拦截 | 检查"有效用例率"，确认是否混入了大量无效 Case |
