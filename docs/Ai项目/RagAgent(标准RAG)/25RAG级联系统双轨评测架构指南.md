# RAG 级联系统评测架构与避坑指南 (Ragas实战总结)

> **报告摘要**：本文档完整呈现了生产级 RAG Agent 评测体系的落地实践。随着项目的演进，我们彻底废弃了僵硬的 `gold_chunk_ids` 硬编码匹配模式，全面拥抱 **Ragas 大模型裁判 (LLM-as-Judge)** 体系。但在深入实践 Ragas 的过程中，我们遭遇了生成参数限制 (`n=1` 报错) 与合成测试集幻觉 ("0召回率高精度"悖论) 等核心挑战。本文档旨在梳理 Ragas 四大指标的真实底层逻辑，并提供可复用的排雷方案。

## 一、 Ragas 评测的核心痛点与破局方案

### 1.1 痛点一：大模型底层 API 限制 (n=1 闪退绝症)
* **表现**：在执行 `answer_relevancy` 等指标评测时，Ragas 默认要求大模型并行生成 3 条数据（`n=3` 参数）。然而以 DeepSeek 为代表的国内顶尖大模型出于算力保护，严格限制 API 参数 `n=1`，导致 Ragas 评测中途直接抛出 HTTP 400 (BadRequestError) 崩溃。
* **破局**：更换裁判模型。我们切换至火山引擎接入的 **GLM-5 (glm-5-2-260617)**。该模型在面对 `n=3` 请求时，能够优雅地执行参数降级策略（返回 1 条结果并输出 `Proceeding with 1 generations` 警告），从而在不修改 Ragas 底层源码的情况下完美根治了闪退问题。

### 1.2 痛点二：测试集幻觉 ("0 召回率" 冤案)
* **表现**：某些用例的 `Context Precision (检索精度)` 高达 0.99，但 `Context Recall (检索召回率)` 却为 0。
* **破局**：这是因为合成测试集（由大模型自动生成）的 **标准答案 (Reference)** 存在严重的幻觉或过于刁钻。Ragas 的四项指标对“标准答案”的依赖度截然不同（详见第二章）。解决此问题的根本方法是人工清洗测试集，剔除劣质的标准答案。

## 二、 重新认识 Ragas 的四大核心指标 (底层逻辑揭秘)

在真实的工业打分中，必须严格区分这四个指标对 **"标准答案 (Reference)"** 的依赖程度。

### 2.1 绝对独立组（0% 依赖标准答案，专测生成质量）
这两个指标**完全不看**标准答案，直接评测 RAG 的生成端能力。
* **Faithfulness (忠实度/无幻觉率)**：
    * **算法逻辑**：比对“最终回答”与“检索到的文档片段”。
    * **业务含义**：判断大模型是否在胡编乱造。哪怕没有标准答案，也能测出系统是否严格基于知识库作答。
* **Answer Relevancy (回答相关性)**：
    * **算法逻辑**：比对“最终回答”与“用户的原始提问”。
    * **业务含义**：判断大模型有没有答非所问、避重就轻。

### 2.2 弱关联组（主要看问题，专测检索相关性）
* **Context Precision (检索精度)**：
    * **算法逻辑**：大模型裁判主要看着检索出的文档片段，思考它对于回答“用户的提问 (Question)”是否有帮助。
    * **业务含义**：只要查出来的文档切题，并且排在 Top 位置，精度分数就极高。它**对标准答案的瑕疵非常宽容**。

### 2.3 强绑定组（100% 依赖标准答案，专测召回完整性）
* **Context Recall (检索召回率)**：
    * **算法逻辑**：大模型裁判将“标准答案 (Reference)”拆分为多个核心论点，然后去检索出的文档里“玩找茬”。
    * **业务含义**：纯粹的应试教育指标。一旦合成的标准答案存在幻觉（比如凭空捏造了几个知识点），裁判在真实文档中找不到对应内容，就会直接判 0 分。**这是受测试集质量污染最严重的指标。**

## 三、 评测拦截门禁与级联失效防护

### 3.1 为什么需要评测前置门禁？
在 LangGraph 架构下，我们设计了严格的主体识别（实体链接）机制。
* **链路特征**：当提问中无法提取到有效实体（如：“那个红色的多少钱”），系统将直接短路，返回兜底澄清话术，不再进入后续检索和生成。
* **评测灾难**：如果把这些被系统主动拦截的 Case 强行喂给 Ragas 打分，由于上下文为空，所有指标将暴跌至 0，严重污染全局平均分。

### 3.2 `evaluate_ragas.py` 的数据清洗策略
在调用 Ragas 官方 `evaluate()` 之前，脚本会执行预检过滤：
1. 校验 `state["item_names"]`，若系统返回的实体为空，则判定为**系统主动拦截 (主体识别失败)**。
2. 在日志中输出拦截警告：`❌ [主体识别失败/系统拦截] ... 已剔除 Ragas 评估`。
3. 将该用例从最终交卷名单中移除，确保 Ragas 打分的均值纯净度。

### 6.2 真实业务场景举例

以下类型的 Query 极易触发"实体识别失败→直接拦截"：

| 类型 | 示例 | 为什么失败 |
|:---|:---|:---|
| **指代不明** | "那个红色的多少钱" | 没有上下文指代对象，"那个红色的"无法映射到产品实体 |
| **口语化缩写** | "P15 咋样" | 实体映射表未覆盖 "P15" → "Product_Pro_15" |
| **超纲实体** | "iPhone 15 支持 WiFi 7 吗" | 知识库里没有 iPhone 15 的任何文档 |
| **跨领域问题** | "今天天气怎么样" | RAG 系统仅做产品知识库问答，天气超出能力边界 |
| **语义模糊** | "你们最好的产品是什么" | "最好的"是主观描述，无法映射到具体产品实体 |

### 6.3 解决方案：测试集有效性预检门禁

在评测主循环中，通过 `validate_case_entity_recognition()` 函数识别哪些 Case 会被系统拦截：

```python
def validate_case_entity_recognition(case: dict, result_state: dict) -> tuple:
    """
    校验当前测试用例的主体/实体识别是否成功，判定其是否具备进入下游检索与生成链路的有效资格。
    
    原理：在 LangGraph RAG 级联图中，若实体识别失败，工作流会直接短路拦截返回，
    不会执行 RRF 召回与 Rerank 精排。因此需要将此类用例拦截，剔除其下游指标计算。
    """
    gold_entities = case.get("gold_entities", [])
    actual_entities = result_state.get("item_names", [])
    options = result_state.get("options", [])
    
    hit_set = set(actual_entities) & set(gold_entities)
    
    # 门禁 1：黄金实体必须非空
    if not gold_entities:
        if options:
            return False, "触发了二义性澄清流程 (options)，系统未进入下游检索"
        return True, "黄金实体未标注，默认视为成功"
        
    # 门禁 2：系统必须至少识别出一个黄金实体（核心门禁）
    if not hit_set:
        return False, f"主体识别失败 (系统识别: {actual_entities}，黄金标准: {gold_entities})，导致链路拦截"
        
    # 门禁 3：系统不能触发澄清流程
    if options:
        return False, f"触发了二义性澄清选项 (options: {options})，未能直接进入检索"
        
    return True, "主体识别成功，正常进入检索与生成链路"
```

### 6.6 踩坑经验总结

| 教训 | 根因 | 解决方案 | 状态 |
|:---|:---|:---|:---|
| **"坏 Case"导致所有指标崩塌** | 实体识别失败→系统拦截→下游数据全空 | `validate_case_entity_recognition()` 预检过滤 | ✅ 已集成 |
| **指标低分不代表系统差** | 测试集质量不可控 | 报告中标注有效用例率 | ✅ 已集成 |
| **Faithfulness 被澄清话术拉低** | 拦截 Case 的 answer 不是真实回答 | 仅对有效用例计算 E2E 指标 | ✅ 已集成 |
| **Rerank 指标依赖标注精度失效** | `gold_chunk_ids` 标注为实体全量切片而非截断维度标准答案 | 移交 Ragas Context Precision | ✅ 已调整 |

**核心认知**：

> **评测脚本本身也是被测系统的一部分。** 当系统有"快速失败"机制时，评测脚本必须理解并适配这一机制，而不是机械地计算所有 Case 的平均值。
>
> **"坏 Case"的 0 分不代表系统检索能力差，只代表"这条 Case 本来就不该被评测"。** 区分这两者，是评测体系设计的基本功。


## 七、 结论与最佳实践

### 💡 结论 1：指标职责分工是核心设计决策

| 指标 | 负责引擎 | 核心理由 |
|:---|:---|:---|
| 实体识别准确率 | 自研 | Ragas 不感知 LangGraph 节点状态 |
| RRF 粗排召回率 | 自研 | Ragas 不检测粗排阶段 |
| Rerank 截断质量 | Ragas Context Precision | 不依赖 `gold_chunk_ids` 硬标注，语义级评估更客观 |
| Faithfulness / Relevance | 双轨交叉验证 | 相互校验，确保可信度 |

### 💡 结论 2：评测体系必须适配系统链路特征

> 当系统有"实体识别失败→直接拦截"的快速失败机制时，评测脚本必须理解这一机制，并在指标体系上做出相应设计——**区分"被测系统的问题"和"测试集本身的问题"**。

### 💡 结论 3：测试集质量是评测体系的基石

所有指标的有效性，都建立在测试集质量可控的前提下。**评测脚本的第一道防线，是验证测试集本身是否有效。**

### 💡 结论 4：生产级双轨策略

| 场景 | 使用工具 | 职责 |
|:---|:---|:---|
| **日常开发/调参** | 自研脚本 | 监控实体识别 + RRF 召回，精准定位问题节点 |
| **阶段性汇报/对外** | Ragas | 输出 Context Precision 等标准指标，对齐业界 |
